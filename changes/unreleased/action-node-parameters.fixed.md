- An assignment, a `while` or `loop` action and a `for` loop own the parts of their statements as parameters, as an `if` action already did: `GetElementProperties` returns two `parameter`s and `input`s for `assign x := 1;` (the target's and the value's `ReferenceUsage`), three for `while c { … } until d;` (the two conditions and the body's `ActionUsage`, with an empty parameter standing for the condition of a `loop`), and two for `for i in c { … }` (the collection's `ReferenceUsage` and the body) after the variable it owns through a `FeatureMembership`. What a loop's braces declare is owned by the body's action rather than by the loop (a body written `action a { … }` is that action, and `while c action a { … }` no longer reads back with a stray `;`), and a conversion writes the same elements, so a graph carries the `ParameterMembership`s and reads back to the same notation. An import written in a loop's braces (`loop { private import Q::*; … }`) now brings its names into that body, where it was ignored, and is the body action's `ownedImport` in `GetElementProperties` as in a conversion. A name such an import brings in is found before the same name in an enclosing namespace (KerML 8.2.3.5.4), and a `for` loop variable's type is resolved where the loop is written, not through its body's imports; neither do they reach the loop's `while` and `until` conditions, and a call in the body is matched against the calculations the body imports.
