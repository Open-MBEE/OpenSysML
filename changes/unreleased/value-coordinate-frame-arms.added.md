- `Value` carries a coordinate frame and a coordinate transformation as themselves, on the new `coordinate_frame` and `coordinate_transformation` arms, where both used to read as unsupported nulls: a frame with its identity, dimensions, per-axis measurement references, measurement scale and the transformation that places it; a transformation with its source and target frames, the shape the model states it in (placement, translation-rotation sequence or affine matrix) and the pose that shape resolves to (`origin + basis · v`, in the source's axis units). A posed part's `coordinateFrame` and a frame's `transformation` therefore reach a consumer structured, over gRPC, Connect, the WebAssembly engine and the MCP runtime tools. The arms are output-only and gated by the `coordinate_frame_values` capability; every client (Go, Python, Node, Java, Rust, Julia, MATLAB) reads them. The clients that define value equality (Go, Python, Node, Java, Rust, Julia) compare frames as the runtime does: by the object and usage read from when there is one, otherwise by dimensions, axes, scale and transformation. Two limits follow from what the wire carries: an `instanceId` means nothing across responses, so the comparison is sound within one response and `frameId` keeps apart different usages, but not two objects of one usage, read in different responses; and a frame's own `transformation` carries no `target`, so it equals a transformation read directly only when both carry the same `instanceId` and `transformationId`.
