- A subrequirement is now an object of its own in the object its containing requirement is: `r.subrequirements` and `r.constraints` hold one object for each nested requirement usage, typed or not, and `r.light.result` is that subrequirement's own check instead of `<undetermined>`. A subrequirement declaring no subject reads its container's (`r.light.v` is what `r.v` holds), at any depth, over a value its definition binds, as the container's check already bound it. Before, an untyped nested requirement held no object, `r.subrequirements` omitted it, and a typed one read its subject unbound.
- A framed concern (`frame concern c : C;`, `frame concern c { … }`, `frame c;`) is now a required constraint of the requirement framing it, checked on that requirement's subject: a requirement whose framed concern fails is violated (`sysml -requirement`), and `r.c.result` reads the concern's verdict. Before, the framing requirement held vacuously and the concern's `result` had no value.
- A chain through a package-level requirement usage that ends at the objects it would hold (`top.subrequirements`, `top.constraints`) is still undetermined, but now of the count the model fixes, so `size(top.subrequirements)` is that count instead of `<undetermined>`.
- An unnamed subrequirement (`requirement : R;`, `requirement { … }`) is held by its container's object as a named one is, so `r.subrequirements` and `r.constraints` count it. A subrequirement of optional multiplicity (`requirement opt[0..1] : R;`, `requirement many[*] : R;`), which the model states no value of, is no longer counted as a required constraint of its container: `RequirementCheck::result` ranges over the values of `constraints`, and the object holds none.
