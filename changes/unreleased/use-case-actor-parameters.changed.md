- **A migrated use case declares its actors.** The SysML v1 migration writes each actor association of a use case as an `actor` parameter nested in the `use case` usage, after its `subject` (written as `subject;` when the use case has actors but no subject, since v2 requires the subject to come first), subsetting the actor's one package-level `part` usage with the end's multiplicity — `actor operator :> Operator;`, `actor attendant [0..1] :> Attendant;` — so the use case reaches its actor in v2 semantics. The actor stays one element: no `part def` and no second usage, so a tool draws it once. The connection written for the association joins the parameter, `connection 'Operator to Control Instrument' connect Operator to 'Control Instrument'.operator;`; an actor end the use case owns is that parameter rather than a second one (named after the actor when it is anonymous); a parameter named after the actor rather than an association end is marked `MigrationMetadata::SynthesizedName` (a comment under `-strict`), and two associations from one actor get distinct parameters. A named association's connection, typed by its `connection def`, still joins the use case usage, as the def's end subsets it. Use-case diagrams draw a use case's subject and actor parameters as pins on its node, as an analysis case's parameters are drawn, so an actor is one node and its association one line ending at the use case.
