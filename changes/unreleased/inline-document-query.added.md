- A document query can be written in place of a name on every surface that runs one: `sysml -run-inline-query '<expression>'`, the REPL's `%run-query inline <expression>`, `RunDocumentQueryRequest.inline_query` on the gRPC `RunDocumentQuery` RPC, and `inlineQuery` on the MCP `run_document_query` tool. The expression is the result expression of a `calc def` specializing `DocumentQueries::Query` — `Project(WhereType(Descendants(Named("Vehicles")), "PartUsage"), ("name", "mass"))` — planned by the same `queryplan` compiler and run by the same `queryexec` executor as a named query, in the loaded model's context: the `DocumentQueries` library imported, the model's own names reachable, and the session's held objects behind `Objects`, `Verdicts`, `States` and `Events`. A path or model fault keeps its QVTS outcome record rather than answering no rows, and text that does not parse or plan is positioned within the expression (`inline query 1:30: expected ')'`), apart from the model's diagnostics. Named and inline forms are exclusive on every surface; the gRPC field is additive and advertised as the `inline_document_query` capability, which the Go (`Client.RunInlineDocumentQuery`), Python (`Model.run_document_query(inline_query=…)`), Node (`Model.runInlineDocumentQuery`), Java (`Model.runInlineDocumentQuery`), Rust (`Model::run_inline_document_query`), Julia (`run_document_query(model; inline_query=…)`) and MATLAB (`runDocumentQuery(model, '', 'inlineQuery', …)`) clients check before sending, with a conformance scenario per protocol.
