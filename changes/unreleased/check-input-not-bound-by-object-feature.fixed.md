- **A constraint or requirement input is no longer bound by a feature of the checked object that happens to share its name.** Checking `constraint masked { in limit : Integer; limit > 4 }` on a part with its own `limit` used to pass over the part's value; the body's `limit` is the parameter (KerML 1.1 §8.2.3.5), which only an argument, a default or a binding the usage states supplies (SysML v2 §7.20.1), so the check — `%constraint`, `-constraint`, `VerifyConstraint`, `VerifyRequirement`, a `satisfy` — now reports `unbound parameter` naming the input. Likewise a requirement feature with no value of its own is no longer read from the satisfying object's same-named feature and reports `no value for feature …` (SysML v2 §7.21.1). **Models relying on the name match need the binding stated:** give the requirement a subject and bind the feature (`subject lander : Lander; attribute :>> verticalSpeed = lander.verticalSpeed;`), read the subject directly (`lander.verticalSpeed <= max`), bind the input on the usage (`in limit = Rig::limit;`), or pass it as an argument. A constraint that declares no such input and names a feature of its context directly is unaffected.
