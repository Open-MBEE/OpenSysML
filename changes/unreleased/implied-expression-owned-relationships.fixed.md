- The elements an expression owns take the implied relationships of KerML 1.1 §8.4.2 Tables 8, 9 and 11 for every reader of the semantic model: an expression is typed by the function it invokes; its parameters redefine that function's by position, or by name for a named argument (`checkFeatureParameterRedefinition`), and its result redefines the function's result (`checkFeatureResultRedefinition`); the result of a feature reference expression subsets the feature it refers to; the result of a constructor expression specializes the instantiated type, and each feature it owns redefines that type's feature (`checkConstructorExpressionResultFeatureRedefinition`); an operand takes the featuring types of the parameter it values (`checkExpressionTypeFeaturing`). Inheritance, redefinition and derived featuring types read these, so the reflective `ownedElement` of a constructor's result lists the features its arguments value. The rows a feature chain expression's target feature would carry are not derived, the model holding no such element. No export or round trip states the implied relationships as elements yet. Readers of the semantic model, `GetElementProperties` among them, therefore answer the name (`x`, `result`: KerML 8.3.3.3.4 effective name) and the inherited type of an expression's parameters and result, which the default export does not write; a recursive import no longer imports two expression results that collide on the name `result`. The condition of a filter package (`expose X::**[@M]`) is owned by the package through its filter membership, where it had no owner.
