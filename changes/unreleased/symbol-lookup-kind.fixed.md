- `GetSymbol` and `GetElementProperties` now take what they name an element by as a stated kind, a qualified name or an element id, instead of one string that is either. A generated id is spelled from names — an unnamed connector end's is `Col__V__c_pend0`, an unnamed member's `Owner::@3` — and a declaration can take the same spelling (`package Col__V__c_pend0`, `part '@3';`), so in the one-string form the declaration shadowed the element the id was reported for. The new `lookup` of `GetSymbolRequest` and `GetElementPropertiesRequest`, a `LookupKind` of `LOOKUP_KIND_QUALIFIED_NAME` or `LOOKUP_KIND_ELEMENT_ID`, has `symbol_id` (`element_id`) read only as a name or only as an id, as the SysML v2 API & Services keeps `@id` apart from `qualifiedName`; the `symbol_lookup_kind` capability advertises it. Every generated id keeps its spelling, so the symbol API, `GetElementProperties` and the `api-json` and RDF exports go on reporting one id for one element. Ids are kept distinct on the declaration's side: a member declared `'@3'` is reported as `Owner::'@3'`, as the notation writes its qualified name, apart from the unnamed member `Owner::@3` that it used to hide, and a root declaration named like another element's element-form `@id` is reported under its own element-form `@id` (`Col_5f_5fV_5f_5fc_5fpend0`). Every id a `childIds` or `members` entry reports now names, as an element id, the element it was reported for, and every declaration answers to its qualified name. A request stating no kind is read as before, name first for `GetSymbol`. In the clients: `get_symbol(name=…)` / `get_symbol(id=…)` and `get_element_properties(name=…)` / `(id=…)` in Python, `symbolByName` / `symbolByElementId` and `elementProperties({ name })` / `({ id })` in TypeScript, `ByQualifiedName()` / `ByElementID()` and `ElementPropertiesByName` / `ElementPropertiesByID` in Go, each asked in the legacy form of a service without the capability; navigation over children, members and specialization targets asks by element id.
