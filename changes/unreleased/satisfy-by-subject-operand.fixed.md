- The `by` operand of a satisfy usage is a feature reference or feature chain (SysML.xtext `SatisfactionReferenceExpression`), and one written as a wider expression (`satisfy requirement sr : R1 by sub#(1);`, `by (a, b)`, `by parts->first()`, `by self.items#(2)`, `by new Sub()`) is now reported once, where the chain ends, with the usage closing at its `;` so the members after it parse undisturbed, instead of a cascade of three diagnostics about the declaration, a metadata prefix and a body member; a `by` subject the next line's member follows is still reported as the missing `;` it is.
- A satisfaction declared with its requirement definition as type (`satisfy requirement sr : R1 by s;`, SysML v2 §7.21.4; a `SatisfyRequirementUsage` is a `RequirementUsage`, §8.3.21.10) is checked against the definition's conditions: `-satisfy`, `%satisfy` and `VerifySatisfaction` decide it as they decide `satisfy r by s;`, where they refused it with `no requirement to satisfy`; one whose definition states no condition reports `no condition to evaluate`.
- Reading `result` on a satisfy usage (`touchdown.result` over `satisfy requirement touchdown : Touchdown by gentle;`, at package level or through the object owning it, `mission.touchdown.result`) evaluates the requirement's conditions with every subject it declares bound to the object `by` names, or to the owning object for a satisfy usage declared without `by` (§7.21.4, §8.4.17.3; `Requirements.sysml` `RequirementCheck::result`), so it reads the verdict the satisfaction check decides instead of `<undetermined>` for the unbound subject; a negated satisfaction's `result` is the requirement's own verdict, never inverted (`Requirements.sysml` `notSatisfiedRequirementChecks`), the negation deciding only whether the assertion holds.
