- A send action (`action a send x via p;`, `send x to q;`, a state's `entry send`, a transition's `do send`) is now a `SendActionUsage` on every surface, not a plain `ActionUsage`: the symbol's kind is `sendActionUsage` and its metadata states the `payload`, `sender` (`via`) and `receiver` (`to`) as written; the query `@type` is `SendActionUsage` and `payloadArgument`, `senderArgument` and `receiverArgument` are queryable; `x meta SysML::SendActionUsage` holds and reflection derives `payloadArgument`, `senderArgument` and `receiverArgument` from the `in` parameters the send owns in argument order (payload, sender, receiver, with an empty sender parameter when only `to` is written), which its `parameter`, `input`, `ownedFeature` and `ownedMember` list before the parameters the send's body declares; the API JSON and Turtle write that structure (`ParameterMembership` → `ReferenceUsage` → `FeatureValue`) as the pilot does, in place of the private `sysx:payload`, `sysx:receiver` and `sysx:isVia` properties, and read it back from the ordered parameters; a named send with a body (`action a send x via p { in x; }`) is one `SendActionUsage` owning the body's members there too, where the API JSON and Turtle wrote an `ActionUsage` around an unnamed send.
