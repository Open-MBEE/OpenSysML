- A truncated or failed answer from PyPI no longer fails a CI job. Every `pip install` of the workflows and composite actions (uv, JupyterLab, the Python client's test tooling, grpcio-tools, fmpy, the documentation toolchain, the snapshot's and the release's build tooling) goes through one action, `.github/actions/pip-install`, that restores a directory of exactly the pinned wheels from the Actions cache, keyed on the request and the interpreter, and installs from it with `--no-index`, so a warm run asks PyPI nothing. On a miss `scripts/ci-pip-install.sh` downloads the set wheel-only in up to four bounded attempts, which pip's own `--retries` does not do for an index page or a wheel that arrived truncated, checks every wheel, and installs only from a complete set; a run PyPI never answers fails with nothing installed. The editable installs of the two Python packages and the virtualenvs the nightly and the PyPI release check their wheels in read the same wheels under `PIP_NO_INDEX`. A new workflow, `.github/workflows/pip-cache.yml`, alone saves the entries on `develop`, on each push that changes a workflow, an action or a pinned file, and daily, and installs each set a second time with the index unreachable. `scripts/ci-pip-install-test.sh` plays the truncated answer against a stand-in pip on every pull request, and `tests/hygiene` fails on a direct `pip install` and on a request the cache workflow does not warm. The nightly builds only a commit that carries the action.
