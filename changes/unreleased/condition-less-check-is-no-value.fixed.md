- A constraint that declares no condition — a bare `constraint def Empty;`, a usage typed by it, or a negated constraint stating only assumptions — is now reported as *no value* (`ErrNoValue`), the error an unbound calc result reads as, instead of the distinct `no condition to evaluate` verdict. A constraint is a `BooleanEvaluation` whose `result : Boolean[1]` only its body expression binds (KerML 1.1 7.4.8.2, SysML v2.1 7.20.2), so without one nothing binds the result; "no conditions" is not a notion the specification has. The cause stays in the diagnostic (`constraint empty: no value: the constraint declares no condition`; a `return r;` the body never binds adds the same hint a calc's does), on every surface that reports a check — REPL `-constraint`/`-requirement`/`-satisfy` and `%check`, LSP, gRPC `VerifyConstraint`/`VerifyRequirement`, MCP `verify_constraint`/`verify_requirement`, the solver, the `smt` engine and the validation report. A requirement, satisfaction or viewpoint with no `require` constraint still holds vacuously (its library result is `allTrue(assumptions()) implies allTrue(constraints())`), an `assume r0;` subrequirement that requires nothing included, and the solver now denies that vacuous claim as `(not true)` — unsatisfiable, as the evaluator reports `assert not satisfy` of it violated — instead of refusing the denial.
