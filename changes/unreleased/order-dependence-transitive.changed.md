- The order-dependence marker now follows the data: a value computed from an order-dependent one stands on the same choice points and prints with the same marker — `y = 2 (order-dependent; 2 choice points — explore shows the set)` after `assign y := x + 1` where two unordered writers wrote `x` — through assignments, the guards of decisions, `if` and loop conditions and transitions (what the selected branch writes stands on what the guard read), a performed action's inputs and outputs, the payload a `send` carries to the `accept` that binds it, and a state machine's effects. A value nothing order-dependent reached stays bare, a merge or join adds no dependence, and a write that reads nothing order-dependent clears the mark of what it rewrites. The marker is the same typed field on every surface (the CLI and REPL, the trace, `order_dependent` over gRPC/Connect, the Python and Node clients, the MCP `execute_action` and `execute_state` tools); the `choice-point` diagnostic's `order_dependent` list still names what the choice itself touched. A performed node's pins report as `node.pin` (`doIt.x`), each performance holding its own, and an invocation's written arguments (`Add(x = 5)`) are what its input pins stand on. Conformance cases state derived marks as `orderDependent`.
