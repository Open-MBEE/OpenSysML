# Performance profile, September 2026

A CPU and allocation profile of the subsystems the two earlier performance
records do not cover: user-model indexing and name resolution, the action and
state interpreters, batch constraint and requirement checking, the gRPC/Connect
and REPL request paths, the lexer and parser on large user models, and the
memory footprint of the language server. Each area closes with the concrete
optimizations the profile supports, an effort estimate, and the semantic risk
each would carry. Where a subsystem is already fast, the record says so.

Two subsystems are **deliberately out of scope** because separate work was
optimizing them while this profile was taken: calc expression evaluation
(`runtime.Value`, literal and target caches, evaluation frames) and standard
library start-up (`internal/workspace/libs`). Where they appear in a profile below
they are named but not analyzed; their opportunities are recorded in
`docs/project/execution-performance-2026-09.md`.

Everything in this record is a **fresh measurement** unless a paragraph says
"historical", in which case it cites `docs/internals/performance.md`,
`docs/project/performance-census-2026-09.md` or
`docs/project/execution-performance-2026-09.md`.

## Methodology

**Machine.** Intel Xeon Platinum 8559C, 8 CPUs, Linux/amd64, Go 1.25.0, the
same processor family as the two earlier records, so absolute figures compare
directly with them. Treat them as ratios elsewhere.

**Revision.** Sections 1–6: `main` at `7ccf3c6f`, with the benchmark package
this record adds (`internal/perfbench`) and no other change. The PGO section
was re-measured on `main` at `80e0450a`, after the calc-evaluator and
standard-library start-up work of the same month had merged. Those two areas
are out of scope here, but figures in sections 1–6 that include library
start-up (an empty `-validate` run, process RSS at start) predate the embedded
snapshot and are higher than the current binary's.

**Workloads.** Two models, chosen so every area has one real and one large
input:

- *vehicle* — `examples/pilot-corpora/sysml-examples/Vehicle Example/SysML v2
  Spec Annex A SimpleVehicleModel.sysml`, the largest pilot-corpus model
  (73 568 bytes, 10 851 tokens). Real structure: deep specialization, many
  imports, small packages.
- *synthetic* — 1 000 blocks generated by `syntheticModel` in
  `internal/perfbench/workload_test.go` (1.42 MB, 53 003 lines, 468 018 tokens,
  32 001 symbols). Each block is a `part def` with three attributes, a nested
  part and two constraints, a `requirement def` with a subject and a `require
  constraint`, a `calc def`, an `action def`, an `action` usage with a
  `for` loop, a `state def` with guarded timed transitions, a `part` usage
  exhibiting the machine, and a `satisfy` assertion. Everything sits in one
  package with `private import ScalarValues::*`, which makes it flat and wide:
  the shape that exposes anything scaling with package size. The model is
  valid; `TestSyntheticModelValidates` keeps it so.

**Benchmarks.** All numbers come from `internal/perfbench`, a benchmark-only
package committed with this record so the figures can be re-taken:

```bash
go test ./internal/perfbench -run '^$' -bench . -benchmem
```

**Profiles.** Each family was run under the Go profiler and summarized with
`pprof`; the tables below are `-top -nodecount=10` output, trimmed to the
columns that matter (`flat`, `cum`, symbol), plus a cumulative view of the
project's own frames where the flat top-10 is only allocator and collector
internals. The loop that produced them:

```bash
go test -c -o perfbench.test ./internal/perfbench
./perfbench.test -test.run '^$' -test.bench 'BenchmarkParse' -test.benchmem \
  -test.benchtime 10x -test.cpuprofile parse.cpu -test.memprofile parse.mem
go tool pprof -top -nodecount=10 perfbench.test parse.cpu
go tool pprof -top -cum -nodecount=60 perfbench.test parse.cpu | grep OpenSysML
go tool pprof -sample_index=alloc_space   -top -nodecount=10 perfbench.test parse.mem
go tool pprof -sample_index=alloc_objects -top -nodecount=10 perfbench.test parse.mem
```

with `-test.benchtime` of `20x` (lexer), `10x` (parser, indexing), `3x`
(analysis, workspace edits, REPL), `200x` (FQN and lookup), `1x` (effective
features, instantiation, satisfaction) and `2s` (lowering, executors,
constraints, gRPC, Connect). Every profile table is labelled with the family
it came from.

**Memory.** `bin/sysml -memstats` for the CLI (Go `runtime.MemStats` after the
run), `/usr/bin/time -v` for OS peak RSS, and for the language server a stdio
driver that sends `initialize`, `didOpen` and five full-document `didChange`
notifications, waits for each `publishDiagnostics`, and reads `VmRSS`/`VmHWM`
from `/proc/<pid>/status` after each step, with `GODEBUG=gctrace=1` on stderr
for the collector's own account.

**A note on GC share.** Every CPU flat top-10 below is led by
`runtime.scanobject`, `findObject`, `gcBits.bitp` and `mspan.base`: 25–40% of
samples across the board are the collector. That is the single most uniform
finding of this profile, and the reason allocation counts are reported beside
every timing. Section 6 quantifies it and what `GOGC` buys.

### Reading

**Name resolution is the cost of analysis, and analysis is the cost of an
edit.** `NameResolutionPass` is 35% of `Analyze` and 29% of a workspace edit;
inside it, `walkUnqualifiedHiding` → `matchImport` dominate: every qualified
reference walks the importing scope's visible-member set, and for the synthetic
model that set is the ~5 000 top-level members of `Perf` plus the wildcard
closure of `ScalarValues`. Two allocation sources are pure overhead of that
walk: `Scope.AnonymousMembers` (builds a fresh slice on every call; 16–19% of
bytes in both families) and `strings.(*Builder).grow` / `strings.genSplit`
(splitting and re-joining qualified-name strings; the top object count).

**`FQNOf` allocates exactly once per call and costs 38 ns**, at the cost of one
`strings.Builder` growth; `LookupQualified` is 40 ns and allocation-free. Both
are fast in isolation. What makes them matter is call volume: qualified names
are recomputed from the scope chain (`joinFQN`, 1.2 M objects during
indexing) and split back into segments (`genSplit`, 0.8–2.0 M objects per
family) rather than kept as segment slices or interned identifiers. A qualified
name does not change after indexing, so caching it on the `Symbol` is the
cheap version of the interning question; integer IDs would additionally
replace the `map[string]` lookups that `mapaccess2_faststr` and `aeshashbody`
represent (5–8% flat in every family), but at a cost that reaches every
consumer of `symbols`.

**Tier 1 effective-feature computation is quadratic in package width, and the
cause is one function.** `Context.findOwnerType` (`internal/exec/runtime/shape.go`)
finds the type that owns a feature by taking the owner scope's *parent*, calling
`MemberNames()` on it — which allocates a fresh `[]string` of every member name —
and scanning them with `LookupLocalAll` until one's `Decl` matches. For a
feature of a type declared at the top of a 5 000-member package, that is a
5 000-entry slice and up to 5 000 map lookups per feature, per type. The
profile is unambiguous: `MemberNames` is 92% of bytes allocated (3.8 GB for
7 000 types) and `findOwnerType` 54% of CPU. `Scope.Owner()` already returns the
owning `Symbol` directly (`internal/semantic/symbols/scope.go`; the builder sets it),
so the scan is redundant. The same function is the top project frame in
sections 3 (`BatchConstraints`, `BatchSatisfy`, `Instantiate`), because every
instantiation materializes features.

**An edit re-does the document, not the edit.** `Workspace.Update` on the
synthetic model reparses and reindexes the whole document (139 ms, 83 MB, 716 k
allocations for a one-line comment appended), and the next `Diagnostics` re-runs
every pass over it (a further 554 ms). Editing a *different*, tiny document
beside it still costs 59 ms and 44.6 MB per keystroke, because the workspace's
index is rebuilt for the open set and the passes for the small document walk
into the large one through its wildcard import. The REPL path is the same
machinery: a 90-byte snippet costs 697 ms and 363 MB against a session that
holds the synthetic model, essentially the full `Analyze` figure. Nothing is
incremental below the document.

*Historical:* `docs/project/performance-census-2026-09.md` recorded the REPL
batch-validation path as quadratic in the number of submissions for the same
reason (each submission reindexes every loaded document), and
`docs/internals/performance.md` recorded that flattening inherited members
eagerly was measured and rejected as a wash. Neither is re-measured here; both
remain consistent with these profiles.

### Opportunities

| # | change | expected gain | effort | semantic risk |
| - | ------ | ------------- | ------ | ------------- |
| 1.1 | `findOwnerType`: use `ownerScope.Owner()` and fall back to the scan only when it is nil | `FeaturesOf` from O(package width) to O(1) per feature: −50% CPU and −90% bytes on that benchmark; the same removal in `Instantiate`, `BatchConstraints`, `BatchSatisfy` (§3). On wide packages the largest single win in this record | small (one function, one test that the fallback is still reached for scopes without an owner) | **low** — `Owner()` is the same symbol the scan looks for; the scan's tie-breaking on duplicate `Decl`s is the only behavior to preserve. Lives in `internal/exec/runtime`, so it must be sequenced after the calc-evaluator work lands in that package |
| 1.2 | `Scope.AnonymousMembers` / `MemberNames`: return the stored slice (or iterate via callback) instead of allocating a copy per call | −16–19% bytes in analysis and edits, less GC pressure everywhere features are enumerated | small–medium: callers that mutate the result must be found | low if the returned slice is documented read-only; the immutable-index invariant already forbids mutation after construction |
| 1.3 | Cache the qualified name on `Symbol` at index time; have `LookupQualified` accept segments so callers stop `Split`ting | removes `joinFQN` (1.2 M objects/index build) and most `genSplit`/`Builder.grow` (the top object counts in every resolution family), roughly −10% allocations in analysis | medium: `FQNOf` callers are many but mechanical | low — the value is a pure function of the scope chain |
| 1.4 | Incremental analysis: keep parse trees and index layers per document and re-run passes only for documents whose dependency set changed | the LSP/REPL per-edit cost falls from "whole open set" to "the edited document plus dependants"; for the small-doc-beside-large case this is the 59 ms → a few ms | high: a dependency graph over wildcard imports, re-exports, redefinitions and identity metadata, plus invalidation; diagnostics timing is a tested contract | **high** — every cross-document diagnostic must be reproduced exactly; needs the differential corpora as the oracle |
| 1.5 | Integer symbol IDs / name interning to replace `map[string]` in hot lookups | −5–8% CPU (hash + compare) in resolution; unclear beyond that | high: touches every `symbols` consumer | medium — mechanical but wide; not justified by these profiles alone. Do 1.3 first and re-measure |

Not worth touching: `LookupQualified` (40 ns, no allocations); the wildcard
expansion for the *user* document (1.6 ms on the synthetic model — the 32 ms on
vehicle is the stdlib closure and out of scope).

### Reading

**There is no lowering cache.** `CreateActionExecutor` calls
`lower.ToActionGraph` every time (`newActionExecutorForOccurrence` → 17% of the
action family, 16.5% of its bytes); the graph for an unchanged declaration is
rebuilt on every run, and the `ExecuteAction` vs `ExecuteActionFreshContext`
gap (11.3 vs 13.7 µs) shows that a warm `Context` saves only the semantic-model
work, not the lowering. For the small `proc1` this is 1.2 µs of an 11 µs run;
for a 1 000-node chain it is 8.2 ms of 8.5 ms — lowering *is* the run.

**Lowering is quadratic in body size.** `LowerChain` goes 0.54 → 1.1 → 8.2 µs per
node from 10 to 1 000 nodes. `resolveActionEndpoint` → `findNodeByReference` →
`findNodeByName` → `nodeAnswersTo` → `getNodeName`/`ast.EffectiveName` is 16% of
the lowering profile: each succession endpoint is resolved by a linear scan of
all collected nodes comparing names, and `collectActionNodes` allocates 19% of
all objects (a slice per nesting level). A `map[string]*ActionNode` built once
per body makes endpoint resolution O(1).

**Per-step cost is allocation, not boxing.** `runtime.Value` boxing does *not*
dominate here the way it does in calc evaluation: `EvalContext.Eval` is 14% of
the action family (the guard and `assign` expressions), and `duffcopy` (6.6%) is
value copying of large structs, but the biggest allocator is
`Sequence.Append` — 30% of bytes — because `for i in 1..10` materializes the
range as a full `Sequence` (`rangeSequence`, 40% of bytes cumulatively) before
iterating. A `1..1000` range allocates 1 000 boxed elements to drive a loop that
touches one at a time. After that: `newStmtEngine` and `initializeAttributes`
allocate a fresh engine and attribute table per body execution, and
`fmt.Sprintf` (4% of bytes, 10 M objects) is diagnostic/identity string
formatting on the hot path.

**The state executor recomputes its active configuration per event.** Every
`ProcessNextEvent` calls `pollChangeEvents` (23% of bytes, 45 M objects),
`activeLeaves` and `activeStates` (27% of objects between them), each of which
rebuilds a slice from the state tree. `NewEvalContext` (18% of bytes) is created
per guard evaluation and per entry action. The 26 allocations per event are
these: none is inherent to firing a transition. `EventQueue.Push`/`eventHeap.Pop`
are a further 10%: a heap is right for timed events, but the `after 1` pattern
here always pops the element it just pushed.

### Reading

**A warm check is cheap; the carrier is not.** One constraint over one already
materialized instance costs 1.3 µs and 6 allocations
(`SameConstraintManyInstances`); the condition text is reparsed by nothing,
the expression is evaluated once. The batch figure of 1.67 µs/check and 9
allocations/check is close to that. What makes batch verification slow is
everything *around* the check: instantiating the subject (2.66 ms per distinct
type, dominated by `findOwnerType` as in §1) and, in the `satisfy` path,
re-instantiating it per assertion. Evaluating 1 000 `satisfy` assertions costs
2.79 s, of which the condition evaluation is a rounding error; 47% is the
owner-type scan and most of the rest is materialization.

**Per-check overhead is strings.** `fmt.Sprintf` is 20% of objects in the
constraint family and `ViolationError.Error` + `conditionText` a further 15%:
the violation message is formatted for every failing check whether or not it is
read, and `conditionText` re-renders the condition from its AST per
evaluation. `beginRun`/`appendConditions`/`chainMembers` (33% of objects
between them) allocate the condition list and a fresh `EvalContext` per check.

**No repeated-subexpression problem worth memoizing.** The synthetic
constraints (`mass > 0.0 and mass < limit`) are as small as real ones; the
profile shows no subtree evaluated more than once per check, and across
instances the subtrees are not pure (they read the carrier's features). The
shape/type of the carrier *is* re-resolved per check — `extractType` and
`declaredType` appear at ~2% each — but the cost is negligible next to the
owner scan. Memoizing pure subtrees would buy nothing on these workloads; the
honest recommendation is not to build it.

### Reading

**The parse cache works, and it is the only sharing there is.** A `ParseFile`
whose content hashes to a cached model returns in 71 µs with 22 allocations;
a miss costs the full 362 ms analysis. The cache key is SHA-256 over the
length-delimited request fields (`parseModel` → `computeHash`), which is
fine, but the *way* it is computed is not: `parseModel` first `Fprintf`s every
field into a `strings.Builder` (`fmt.(*buffer).writeString` +
`strings.(*Builder).Write`, 38% of the family's bytes), then `computeHash`
converts the result to `[]byte` for `sha256.Sum256` (another 19%) — a 73 KB
model is copied three times per request, even on a hit. Writing the same
delimited fields straight into a `sha256.New()` hasher yields the identical
digest and removes 57% of the family's allocation, ~200 KB of the 222 KB a
cached `ParseFile` allocates.

**Every `Evaluate`/`VerifyConstraint` builds a fresh runtime.** `GRPCEvaluate`
allocates 82 KB and 928 objects for a two-argument calc call whose evaluation
is a few hundred nanoseconds; `GRPCVerifyConstraint` allocates 9.4 MB and takes
25 ms because it creates a `resolve.Resolver`, `semantics.Model` and
`runtime.Context` per request (`resolve.New`, `semantics.NewModel`,
`runtime.NewContext` all appear in the Connect object counts) and then
instantiates the subject through the §3 path. The parse cache holds the index;
the resolver and semantic model derived from it are immutable for a given model
hash and could be cached with it. Whether the `runtime.Context` can be shared is
a different question: it carries instances and identities, so per-request
isolation is currently a *feature*, and sharing it would require the context
to be reset or forked per request.

**The REPL reparses the session on every expression.** `REPLEvalExpr` costs
76 ms and 36.8 MB to evaluate `Perf::Calc1(2.0, 3.0)`: `Session.EvalExpr`
joins the session's accepted snippets and the expression into one source and
re-analyses it (`parseUsage`, `parseBase`, `parseQualifiedNameRelaxed` in the
repl allocation profile are the parser re-walking the 1.4 MB model). Against a
session holding the synthetic model that is a tenth of a full load per
expression. The debugger note in `internal/frontend/repl/session.go` (a submission keeps
a running `%action`/`%state` session alive unless it supersedes the behavior
being stepped) means any change here must preserve the existing session's
graph and runtime context identity.

*Historical:* the census recorded the REPL empty-session floor rising
six-fold in the week before this measurement; that floor (1 ms) is invisible at
the scale of the figures here and was not re-measured.

### Reading

**The lexer is done.** 15–25 ns per token, allocation-free, 200–270 MB/s. Its
one lookup is the keyword map; a perfect-hash or switch on length would save
a few nanoseconds per identifier and is not worth the code.

**The parser is I/O-bound on its own token buffer.** `peek`/`peekN`/`fill`/
`atKeyword` are 70% of parser CPU: the recursive-descent grammar looks ahead
several tokens at most decision points (`parseDefUsage` in particular, which
must distinguish definition from usage from relationship), and each look-ahead
goes through the buffered `peekN`. The allocations are the AST itself —
`parseUsage`, `parseBase`, `parseBinary` build nodes, `bodyBuilder.add` grows
member slices, `parseQualifiedName*` allocates one `[]string` per name. String
copies are *not* a cost: `source.(*SourceFile).Text.func1` is 3.7% of bytes
and token text is sliced from the source, not copied.

At 76 ms for 1.4 MB the parser is ~13% of a full analysis of the same model
and ~55% of `Workspace.Update`'s reparse. It is the second-cheapest stage
after the lexer.

*Historical:* `docs/internals/performance.md` recorded that recycling the
parser's token buffer across parses was measured and rejected. The profile
here agrees: the buffer is not the allocation, the look-ahead is the CPU.

### Reading

**Live heap is half of RSS.** With a 1.4 MB model open the server holds
~130 MB live — 52 MB of standard library plus ~80 MB for the model's AST,
index, resolution caches and diagnostics — while RSS sits at 269 MB. The gap is
the collector's headroom (`GOGC=100` lets the heap double before collecting)
plus the garbage of the last edit. Per edit the server allocates ~330 MB
(§1's `reindex+diagnostics` figure), so it is churning 2.5× its live heap on
every keystroke and RSS follows the peak of that churn, not the live set.

**The GC's own CPU share is small; its *memory* share is not.** `gctrace`
puts the concurrent collector at 1–4% of CPU at the default setting — the
`scanobject` samples that lead every §1–§5 profile are the background mark
workers on the other cores, which is why they show as 25–40% of *samples* but
cost little *latency* on an 8-core machine. On a 2-core laptop the same work
would be latency. `GOGC` therefore trades RSS for almost nothing here:
`GOGC=200` saves ~100 ms per edit (−14%) at +140 MB RSS on the synthetic model,
and nothing at all on vehicle; `GOGC=50` saves 40 MB and costs nothing
measurable either way.

**A memory limit is the right knob, and 256 MiB is about the floor for this
model.** `GOGC=off GOMEMLIMIT=256MiB` matches the default's latency
(623 vs 696 ms) at −8% RSS, because the collector runs exactly when needed.
Push it to 160 MiB — barely above the 130 MB live set — and the server falls
off a cliff: 172 collections, 11% GC CPU, edits 58% slower. The limit must
leave ~2× live heap of room, which means it cannot be a fixed number in the
binary: `debug.SetMemoryLimit` set from the container's cgroup limit (or an
`--memory-limit` flag) is the deployable version. Reducing per-edit churn
(opportunities 1.1–1.4) lowers both the peak and the live-set multiple at once
and is worth more than any collector setting.

**Application `MemStats` and OS RSS agree to within 5%** (`HeapSys` 239.9 MiB vs
peak RSS 249.9 MB for the CLI on the synthetic model), so `-memstats` is a
trustworthy proxy where `/proc` is unavailable. Neither includes the ~10 MB
the Go runtime and binary text add.

## Prioritized summary

Ranked by expected gain per unit of risk, across all six areas:

1. **`findOwnerType` via `Scope.Owner()`** (1.1 / 3.1). One function; removes
   an O(package width) scan from every effective-feature computation. Halves
   instantiation and satisfaction CPU and removes 80–90% of their allocation on
   wide packages. Low risk. Sequence after the in-flight calc-evaluator work in
   `internal/exec/runtime`.
2. **Lowering cache + name-indexed endpoint resolution** (2.1 / 2.2). Every
   repeated execution of an action or state machine stops re-lowering; long
   bodies stop being quadratic. −16% on small behaviors, −97% on long chains.
   Low risk; same sequencing caveat.
3. **Stream the cache key into the hasher; cache resolver/model with the
   parsed index** (4.1 / 4.2). Cached `ParseFile` drops from 222 KB to ~20 KB per request and
   `Evaluate`/`VerifyConstraint` stop rebuilding immutable state. Small,
   isolated to `internal/frontend/grpc`, effectively no semantic risk.
4. **Stop copying member lists; cache FQNs** (1.2 / 1.3 / 5.2). −15–20% bytes
   and ~−10% objects across analysis, edits and REPL submissions. Mechanical
   but wide.
5. **Lazy violation messages; per-batch `EvalContext`** (3.2 / 3.3). −60%
   objects per constraint check. Small.
6. **Lazy ranges in `for`; cached active-leaf set** (2.3 / 2.4). Per-step
   allocations in both interpreters fall by a third or more. Medium risk;
   traces are the oracle.
7. **Incremental analysis** (1.4) and **scoped REPL expression evaluation**
   (4.4). The largest user-visible gains (per-keystroke latency in the LSP
   and REPL) and the largest risk; each needs the differential corpora as its
   test contract and should be its own design record.

Not recommended on this evidence: memoizing pure constraint subtrees (§3),
integer symbol IDs ahead of FQN caching (1.5), raising `GOGC` (§6), or any
lexer work (§5).

## Profile-guided optimization

The one change this record ships: `cmd/sysml/default.pgo`,
`cmd/sysml-lsp/default.pgo` and `cmd/sysml-grpc/default.pgo`, one merged CPU
profile (301 s of samples) of the package test suites, the `internal/frontend/repl`,
`internal/frontend/grpc` and `internal/perfbench` benchmarks, and the CLI validating
every model in the checkout and evaluating three expressions. `go build` in
Go 1.21+ applies a `default.pgo` beside a main package automatically
(`-pgo=auto`); `scripts/pgo-profile.sh` (`make pgo-profile`) regenerates it,
see `DEVELOPING.md`.

**Method.** Before is `-pgo=off`, after is the committed profile, same
revision (`main` at 80e0450a, which already carries the sibling calc-evaluator
and embedded-stdlib-snapshot work), same machine, nothing else running.

(`go test -c -pgo=off` / `-pgo=cmd/sysml/default.pgo`). CLI and LSP: the two
binaries run alternately, 11 runs each, median of the `-memstats` wall time or
the driver's `didOpen`→`publishDiagnostics` time.

go test ./internal/frontend/repl -run '^$' -bench . -benchmem -count 6 -pgo=cmd/sysml/default.pgo > after.txt

**Reading.** PGO pays where the profile has hot, inlinable call chains: the
executors, constraint checking, calc invocation inside the REPL (−9% to −25%),
and it removes allocations outright where inlining lets escape analysis keep a
value on the stack (`RunCalc` 25 → 23 allocs, `LoadModel` −4.9%,
`Analyze/synthetic` −6.6%, `ExecuteState` −7.3%). It does nothing measurable
for the parser, the workspace pipeline or the whole-binary wall times, whose
cost is spread over thousands of small frames and the collector; the parser
trends 1–3% slower across both runs, consistent with the code-size growth,
though only the first run reached significance. The stdlib-load and
marginal-calc figures are within run-to-run noise in both directions; the
embedded snapshot has already taken stdlib load to ~14 ms, so there is little
left for PGO to find there. Net: a modest, real win on execution-heavy paths
for +0.8–1.0 MB per binary, and no semantic exposure. Refresh the profile
when a hot path changes shape.

One toolchain caveat: a coverage-instrumented `go test ./...` that includes a
main package carrying a `default.pgo` fails to link that package's test binary
(`link: fingerprint mismatch`, golang/go#80891, open as of Go 1.25). `make test`
and `make coverage` therefore pass `-pgo=off`; tests run against the same code
either way, minus the profile-driven inlining.

## What was not measured

- Calc expression evaluation and standard-library start-up, by design.
- Peer-to-peer LSP features (completion, hover, references) — the driver
  exercised only the open/change/diagnostics path.
- The gRPC transport proper (`google.golang.org/grpc` over HTTP/2); the Connect
  handler over HTTP/1.1 stood in for it.
- A machine with fewer cores, where the collector's 25–40% of samples would
  become wall time.
- The REPL debugger (`%action`/`%state` stepping) — its per-step cost is the
  executor's, measured in §2, but the session-carry logic was not profiled.
- Standard-library load time under PGO was measured only as the `-validate`
  wall time of an empty file (parse + index + resolve of the bundled library);
  the phases inside it were not separated, since that path is the sibling
  work's.
