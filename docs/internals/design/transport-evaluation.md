# Transport evaluation: Connect and stdio beside gRPC

**Date:** 2026-08-25
**Status:** Evaluation — prototypes behind flags, **not** a migration
**Scope:** `cmd/sysml-grpc`, `internal/frontend/stdiorpc`, `internal/frontend/grpc/connect.go`, `client/python/scripts/bench_transports.py`

---

## 1. What this is and is not

Clients are planned in TypeScript, Java, Rust and Go beside the existing Python one, and two
properties of today's transport would be paid once per client: gRPC is not reachable from a
browser, and a service that listens on a TCP port makes every client manage a port, a health
probe and an ownership record. This document measures both, from working prototypes, and
recommends.

Nothing here migrates anything. The grpc-go server is untouched and remains the default; both
prototypes are additional values of one new flag, and no client in the repository changes.

```
bin/sysml-grpc                      # grpc-go, exactly as before  (default)
bin/sysml-grpc -transport connect   # gRPC + gRPC-Web + Connect on one port
bin/sysml-grpc -transport stdio     # frames on stdin/stdout, no port at all
```

## 2. Verified premises

Every premise was checked against the code rather than assumed. One is wrong.

| Premise | Verdict |
|---|---|
| `sysml.proto` defines `service SysMLService` with **17** RPCs | ✗ **15**, see below |
| all RPCs unary, no streaming | ✓ no `stream` keyword anywhere in the file |
| proto3, scalars plus `oneof` and `map<>` only | ✓ `oneof source`, `map<string, Value>`, `map<string, string>` |
| `cmd/sysml-grpc` serves plain grpc-go with `-port`/`-health-port`/`-cache-size`/`-log-level` | ✓ |
| no TLS, no auth | ✓ `insecure` on both ends, no credentials or interceptor for either |
| `connection.py` is ~1,710 lines, largely port lifecycle | ✓ exactly 1,710; ~690 are port lifecycle (§6) |
| `cmd/sysml-lsp` already speaks stdio as a child process | ✓ `stdio{}` over `os.Stdin`/`os.Stdout`, logs to stderr |
| `bench_latency.py` reports p50/p95/p99 over a warm channel, setup excluded | ✓ and this evaluation keeps that split |

### 2.1 The RPC count is 15, not 17

`api/proto/sysml.proto` declares fifteen: `GetServerInfo`, `ParseFile`, `GetSymbol`,
`GetDiagnostics`, `Evaluate`, `Instantiate`, `ExecuteAction`, `ExecuteState`, `Convert`,
`ApplyEdits`, `VerifyConstraint`, `VerifyRequirement`, `VerifySatisfaction`, `EvaluateCalc`,
`Query`. The difference does not change any conclusion — all fifteen are unary, which is the
property the streaming analysis in §8 turns on — but the number is quoted in planning material
and is wrong there.

## 3. The Connect prototype

`-transport connect` serves the same `sysml.proto`, the same service implementation and the same
port, through `connect-go` instead of `grpc.NewServer`:

- `internal/frontend/grpc/connect.go` — a `ConnectAdapter` wrapping the existing `*Service`. Each of the
  fifteen methods unwraps `*connect.Request[T]`, calls the existing handler and re-wraps, mapping
  gRPC status codes onto Connect codes. The service itself is unaware of either.
- `api/proto/protoconnect/` — bindings generated by `protoc-gen-connect-go` from the **unmodified**
  proto. `generate.go` holds the `go:generate` line; the parallel `buf` migration should own the
  invocation rather than this directory.
- `cmd/sysml-grpc/connect.go` — one `http.ServeMux` behind `h2c`, so cleartext HTTP/2 (what an
  existing gRPC client needs against a port with no TLS) and HTTP/1.1 are both served.

Three protocols and reflection come off that one handler; `/health` is served on the same port,
which removes the *reason* for the separate 8081 health port. The prototype still binds it, so
`/health` currently answers on both; retiring the second port is available, not yet taken.

`cmd/sysml-grpc/connect_test.go` asserts this rather than describing it: the generated
grpc-go stub — the code path the Python client and `grpcurl` use — works unchanged against the
Connect handler, and the Connect, gRPC and gRPC-Web protocols each answer the same call.

### 3.1 The curl case

Verified against `-transport connect -port 50161`, HTTP/1.1, no gRPC library, no generated code:

```console
$ curl -X POST http://localhost:50161/sysml.SysMLService/ParseFile \
    -H "Content-Type: application/json" \
    -d '{"content":"package Demo { part def Rover { attribute mass = 12.5; } }"}'
{"modelHash":"6245ef4849a9019f3cbc64b03a54880f61d0fc3178f9be9d204d026f8007e78d",
 "root":{"kind":"RootNamespace","childIds":["Demo"]}}

$ curl -i -X POST http://localhost:50161/sysml.SysMLService/Evaluate \
    -H "Content-Type: application/json" \
    -d '{"expression":"1 + 2 * 3","modelHash":"6245ef48...e78d"}'
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 27

{"result":{"intValue":"7"}}
```

Two things a hand-written client has to know: an `int64` is spelled as a JSON **string**
(`"7"`), per proto3 JSON mapping, and a failed call answers with an HTTP status plus
`{"code":"not_found","message":...}` rather than gRPC trailers.

Existing consumers are unaffected on the same port:

```console
$ grpcurl -plaintext localhost:50161 list
sysml.SysMLService
$ curl -s http://localhost:50161/health
{"service":"sysml-grpc","status":"ok","version":"dev"}
```

### 3.2 What a browser still needs

gRPC-Web works, with one precise gap. `connect-go` v1.20 implements `application/grpc-web` and
`application/grpc-web+json`, but **not** the base64 `grpc-web-text` variant — there is no
`grpc-web-text` in the module at all, and posting that content type answers `415`:

```console
$ curl -o /dev/null -w '%{http_code}\n' -X POST \
    http://localhost:50161/sysml.SysMLService/GetServerInfo \
    -H "Content-Type: application/grpc-web-text"
415
```

`grpc-web-text` only matters to a client that cannot read binary response bodies (old
`XMLHttpRequest` paths). Any browser client using `fetch` — which is what `connect-web` and
`grpc-web`'s fetch transport do — is unaffected. So a browser client needs: `connect-web` or
`@connectrpc/connect-web` generated from this proto, **CORS** (nothing in the prototype sets
`Access-Control-Allow-*`, and gRPC-Web additionally needs `Access-Control-Expose-Headers` for
its trailers), and TLS in any real deployment, since a browser on an HTTPS page cannot post to
`http://`. None of the three is present today; all three are ordinary work.

## 4. The stdio prototype

`internal/frontend/stdiorpc` serves all fifteen RPCs over a pipe pair, dispatching from
`pb.SysMLService_ServiceDesc.Methods` so no RPC can be forgotten when one is added. Framing is
the one `cmd/sysml-lsp` already speaks: `Content-Length`, headers, blank line, body. Two body
encodings are served so that framing and encoding can be measured apart:

```
Content-Length: 74
Content-Type: application/json

{"jsonrpc":"2.0","id":1,"method":"Evaluate","params":{"expression":"2 + 2"}}
```

```
Content-Length: 31
Content-Type: application/proto
Sysml-Method: Evaluate
Sysml-Id: 1

<the same protobuf bytes gRPC would carry>
```

An answer carries `Sysml-Id` plus `Sysml-Status-Code` (the gRPC code, so clients keep their
error handling) and, when non-zero, `Sysml-Status-Message`. Logs go to stderr; stdout carries
frames only.

### 4.1 Concurrent calls over one pipe

This is a design decision, not a detail, and the two sides of the prototype answer it
differently.

**The server multiplexes.** `Serve` reads a frame, hands it to a goroutine and goes back to
reading, so a slow call does not block the frames behind it. Writes are serialized under a
mutex, one whole frame at a time, so answers interleave at frame boundaries but never
mid-frame. Answers may therefore arrive **out of order**, which is why the id is mandatory and
why `server_test.go` covers a slow call being overtaken by a fast one.

**The prototype client does not.** The Python client in `bench_transports.py` writes a request
and then blocks reading its answer, so at most one call is in flight. That is head-of-line
blocking in its plain form: a 40 ms `Query` issued first delays a 0.1 ms `Evaluate` behind it
by the full 40 ms, whereas over a gRPC channel or an HTTP/2 connection the two are separate
streams and the second answers immediately. A real client fixes this the way every LSP client
does — a reader thread demultiplexing by id into per-call futures, plus a writer lock — which
is roughly 40 lines and is precisely the code §6 counts as newly owed.

Backpressure is real in both directions: a client that stops reading fills the OS pipe buffer
(64 KiB by default on Linux) and blocks the server's writer goroutine, which the 468 KB `Query`
answer of §5 exceeds by seven times. A client must keep draining stdout even while it is
sending.

### 4.2 What stdio gives up

One service per client process, so N notebooks parse the same model N times and the semantic
cache is not shared — today an adopted service is shared. No remote or containerized service,
no multi-language access to one process, no `curl`, no reflection, no interception by anything
that speaks HTTP. And the framing, correlation, multiplexing and cancellation semantics are
ours to specify and to test in every client, where gRPC and Connect ship them.

## 5. Measurements

`client/python/scripts/bench_transports.py` — a new harness rather than an extension of
`bench_latency.py`, because that script takes a live `Connection` (which implies TCP and the
whole ownership path) and cannot express three transports, four operations and cold-start
spawning. It keeps the property its docstring insists on: setup is measured separately, and warm
numbers are per-call with the connection already established, protobuf/JSON encode and decode
included. Percentiles, not means.

**Method.** One `bin/sysml-grpc` binary, one machine, 8 CPUs, otherwise idle (load average
0.05–0.12). 200 iterations per cell, one discarded warm-up call. 10 spawns per cold-start cell,
each measured spawn → first successful `GetServerInfo`. Small model: the 20 part definitions
`bench_latency.py` builds. Large model: `SysML v2 Spec Annex A SimpleVehicleModel.sysml` from
`examples/pilot-corpora`, 73,568 bytes. `Query (whole model)` is the large-response case — its
answer is 468 KB of symbols. Full run in `--json` form; the tables below are one run, and §5.3
compares two.

### 5.1 Cold start

| Transport | p50 | p95 | sd |
|---|---|---|---|
| gRPC over TCP (baseline) | 5.8 ms | 8.5 ms | 1.0 |
| Connect, protobuf body | 5.8 ms | 6.2 ms | 0.3 |
| Connect, JSON body | 5.9 ms | 6.3 ms | 0.6 |
| stdio, protobuf body | **3.7 ms** | 4.0 ms | 0.2 |
| stdio, JSON body | **3.7 ms** | 4.3 ms | 0.3 |

stdio starts ~2 ms sooner, consistently: no bind, no health poll, and the pipe is ready when
the child exists. Set against the ~500 ms the Python client's ownership path spends deciding
whether to start a service at all, 2 ms is not the interesting number — the interesting number
is that it is never a *retry* loop.

### 5.3 What is signal and what is noise

**Noise: every small-payload cell.** Sub-millisecond cells move by more than the differences
between transports when the same benchmark is run twice. Between two runs of the identical
harness, `stdio, protobuf / small / ParseFile` p50 went 0.44 → 0.15 ms and
`stdio, JSON / small / Evaluate` went 0.57 → 0.07 ms. Standard deviations (0.15–0.35 ms) are of
the same size as the p50s themselves. **There is no measurable per-call difference between
gRPC, Connect-protobuf and stdio-protobuf on small payloads**, and the apparent 0.2–0.4 ms
advantage of the two prototypes over grpc-go is not one we can claim from this data. Nothing in
this report should be read as a latency argument for changing transport.

**Signal: JSON on a large response.** A 468 KB `Query` answer costs 6.3–6.9 ms in protobuf on
all three transports and 38–40 ms in JSON on both that carry it — **6× slower, reproducible
across runs, with sd ≈ 1.7 ms**. Note *why*, because it is not what the framing of the question
assumed: the bytes barely differ (467,971 protobuf vs 513,339 JSON, +9.7%), so this is not
bandwidth. It is `protojson` encode plus `json_format` decode CPU. Payload size is the *symptom*;
serialization cost is the finding. A browser client, which has no protobuf option over
Connect-JSON, pays it.

**Signal: cold start.** 3.7 vs 5.8 ms, sd ≤ 1.0, holds across runs.

## 6. The lifecycle-code delta

`client/python/opensysml/connection.py` is 1,710 lines. Counted by function, **~690 of them exist only
because the service listens on a TCP port** — 40% of the file. Enumerated, not estimated:

| Responsibility | Functions | Lines |
|---|---|---|
| Parse a `host:port` target, reconcile `host=` and `port=` | `split_target` | 46 |
| State directory, lockfile path, pidfile path, service key | `_state_dir`, `_get_lockfile_path`, `_get_pidfile_path`, `_service_key` | 22 |
| Ownership records: write, read, start-time authentication, removal | `_write_ownership_record`, `_read_ownership_record`, `_started_at`, `_authenticate_record`, `_recorded_service`, `_recorded_by_this_process`, `_remove_service_state` | 101 |
| Readiness: health-port poll, gRPC probe, identify who is listening | `_probe_service`, `_running_service_info` | 65 |
| Release negotiation with a service someone else started | `_required_release`, `_check_managed_service_release`, `_raise_if_release_mismatch` | 48 |
| Ownership and adoption: reference counting, adopt a running service, replace a mismatched one, lose a bind race, detect a service that died, clean up | `_started_by_this_client`, `_owned_service`, `_take_ownership_reference`, `_adopt_running_service`, `_hold_running_service`, `_replacement_serves`, `_replace_mismatched_service`, `_ensure_service`, `_wait_for_a_service_that_could_not_bind`, `_own_spawned_service`, `_service_started_here_died`, `_cleanup_service` | 385 |
| Terminate by pid with a kill fallback | `_stop_process` | 23 |
| **Total** | | **~690** |

Plus roughly 25 of `__init__`'s 64 lines (address, channel, refcount and release fields). The
behaviors documented in the "Service ownership" section of `client/python/README.md` —
"never stop a service you did not start", pid records authenticated by process start time so a
reused pid is never signalled, stale-record cleanup, replacing a wrong-release service — are
**entirely** in that 690. Under stdio the question they answer does not arise: the child is
this client's, its lifetime is the pipe's, and the OS reaps it.

What stays regardless of transport: the fifteen RPC wrapper methods, Python↔`Value` conversion
and gRPC-status-to-exception mapping — roughly 950 lines, none of it transport-specific.

What stdio newly owes, per client language: spawn with three pipes and reap on close (~15
lines), `Content-Length` framing (~20), request-id allocation and correlation (~10, and 40 if
concurrent calls are wanted — see §4.1), stderr drained to a log so a full pipe cannot deadlock
the child (~10), and detecting child death mid-call. The prototype's Python client is 72 lines
including both encodings, single-call-in-flight. Call it **~100 lines against ~690** — a real
saving, roughly 6:1, and it repeats across TS, Java, Rust and Go. But it is 100 lines of
*protocol* code we specify and must conformance-test per language, replacing 690 lines of
*lifecycle* code we already got right once.

## 7. Per-language client impact

| | Today (gRPC/TCP) | With Connect | With stdio |
|---|---|---|---|
| **TypeScript** | Node only, `@grpc/grpc-js`; browser impossible | `@connectrpc/connect-web` in the browser, `connect-node` in Node, one generated client | Node only, worse than today: no browser, and framing is ours |
| **Java** | `grpc-java`, plus the lifecycle port | Connect has no first-party Java client; use `grpc-java` against the same port, unchanged | hand-written framing on `Process` streams |
| **Rust** | `tonic`, plus the lifecycle port | no first-party Rust client; `tonic` against the same port, unchanged | hand-written framing on `tokio::process` |
| **Go** | `grpc-go` | `connect-go`, or `grpc-go` unchanged | straightforward (`internal/frontend/stdiorpc` already exists) |
| **Python** | 1,710 lines, ~690 lifecycle | unchanged (gRPC still served); could drop 8081 | ~690 lines removed, ~100 added |
| **curl / any HTTP tool** | health only | every RPC | not applicable |

The pattern: **Connect's benefit is concentrated in TypeScript** and is decisive there, since it
is the difference between a browser client existing and not. For Java and Rust it changes
nothing — they keep speaking gRPC to the same port. stdio's benefit is spread evenly across all
five and is the *opposite* of what TypeScript-in-a-browser needs.

## 8. If we add streaming later

All fifteen RPCs are unary today (§2.1), so §5 measures only the unary case. What each candidate
would cost if that changes:

### 8.1 Where streaming would plausibly be wanted here

Checked against the code, not hypothesized:

- **`ExecuteAction` — confirmed.** `ActionExecutor.RunToCompletion` in
  `internal/exec/runtime/action_executor.go` loops on `Step()` moving tokens until the graph
  finishes or a step budget trips, and `TraceRecorder.RecordActionStep(step, tokens)` already
  records each step with its tokens. `ExecuteActionResponse` returns one map of outputs after all
  of it. A server-streaming `ExecuteAction` emitting per-step token positions would need no new
  runtime work — the events exist and are already recorded.
- **`ExecuteState` — confirmed.** `ExecuteStateWithEvents` returns `statesVisited` and the final
  context only on completion, while `TraceRecorder` has `RecordStateTransition`,
  `RecordStateEntry`, `RecordStateExit` and `RecordLoopIteration`. The per-transition sequence a
  stream would carry is exactly what is recorded and then discarded.
- **Interactive execution — the strongest case.** The executor supports breakpoints, suspension
  (`StateSuspended`, `pausedAt`) and waiting. A debugger driven over unary RPCs must poll; over a
  stream it is push. Note this is the *bidirectional* case, not server-streaming: the client
  sends `continue`/`step` while the server sends stop events.
- **Incremental diagnostics on a large parse — plausible, not yet supported.** `ParseFile`
  answers in 0.7 ms even for the 73 KB model (§5.2), so today there is nothing to stream.
  Workspace-wide parsing is where this would matter, and `GetDiagnostics` is per-model. The LSP
  server, which does have this need, already pushes `publishDiagnostics` over stdio.
- **`Query` — worth noting.** The 468 KB answer of §5 is buffered whole on both sides. Streaming
  symbols would cap client memory and let a UI paint early. This is server-streaming and needs no
  runtime change.

So: server-streaming has real, code-backed candidates; bidirectional has one clear candidate
(interactive execution) that is a plausible product direction for a debugger UI.

### 8.2 What each transport supports

| | server-streaming | client-streaming | bidirectional | browser can consume |
|---|---|---|---|---|
| **gRPC** (HTTP/2 only) | yes | yes | yes, full-duplex | no |
| **Connect protocol**, HTTP/2 | yes | yes | yes | yes, via `connect-web` |
| **Connect protocol**, HTTP/1.1 | yes | yes | **no** | yes, server-streaming only |
| **gRPC-Web** | yes | no | no | yes |
| **stdio** (pipes) | yes | yes | yes, inherently | not applicable |

The precise statements behind that table:

- **gRPC** requires HTTP/2 and gets all four streaming shapes from it. We pay its weight — an
  HTTP/2 stack, flow control, trailers — and use none of it, which is a real but small cost:
  it is a dependency and a protocol surface, not per-call latency (§5.3).
- **Connect** carries streaming RPCs in an enveloped framing over a single POST. Over HTTP/2 that
  is bidirectional-capable. Over **HTTP/1.1 it is half-duplex**: the request body must be fully
  sent before the response body begins, so server-streaming and client-streaming work and
  bidirectional does not. This is an HTTP/1.1 property, not a `connect-go` limitation. Practical
  consequence: an interactive-execution RPC (§8.1) would require HTTP/2 end to end, which in a
  browser means TLS.
- **gRPC-Web** is server-streaming only by design, in every implementation. A browser client that
  needs bidirectional cannot use it and must use the Connect protocol over HTTP/2.
- **A browser** can consume server-streaming over Connect or gRPC-Web via `fetch` response
  streams. It **cannot** consume gRPC at all, streaming or unary — the reason Problem 1 exists.
- **stdio** is two independent pipes and therefore inherently full-duplex: server push costs
  nothing at the transport level, and `cmd/sysml-lsp` already does exactly this with LSP
  notifications. What it costs is *above* the transport, and streaming makes each item worse than
  it is for unary: framing must gain a "this is one item of response N, and here is its end"
  notion; correlation must route items to a live subscription rather than resolve a future once;
  multiplexing becomes mandatory rather than optional, because a long stream on a single-call
  client would block every other call indefinitely (§4.1); backpressure becomes a protocol
  problem, since a fast producer against the 64 KiB pipe buffer will block the server's writer
  and there is no flow-control window as HTTP/2 has; and cancellation needs a message, since
  there is no per-stream half-close. Each of those is a specification we write and then implement
  and test **five times**.

### 8.3 How streaming changes the recommendation

It weighs clearly **against** stdio-JSON-RPC, and we should say so explicitly: stdio wins cold
start (§5.1) and wins the lifecycle-code count (§6), and it would still be the wrong foundation
if streaming is coming, because the four hand-rolled costs above are paid per client language
and are exactly what gRPC and Connect already solve. Put differently — today stdio owes ~100
lines per client; with streaming and mandatory multiplexing it owes a small protocol
implementation per client, and correlated-multiplexed-flow-controlled framing is a thing to get
subtly wrong five times. Connect, by contrast, gets server-streaming — which is where all the
code-backed candidates are — for free from the same generated code, in the browser included,
with only bidirectional needing HTTP/2.

## 9. Recommendation

**Adopt Connect for the server; do not adopt stdio; keep gRPC as it is.**

The evidence divides cleanly. Latency is not a reason to do anything: on small payloads the
three protobuf transports are indistinguishable within run-to-run noise (§5.3). The one strong
performance finding is a warning about JSON, not about a transport — 6× on large answers, from
serialization CPU rather than bytes.

1. **Serve Connect from `cmd/sysml-grpc`, keeping gRPC on the same port.** Cost: one dependency,
   ~240 lines of adapter and server code, generated Connect bindings, and a second protocol
   surface to test. Gain: a browser client becomes possible, which is the deliverable that has no
   alternative; the service becomes `curl`-able; the separate 8081 health port becomes
   retirable (the prototype still binds it — see §3). Migration risk to existing consumers: **low but not zero, and it is verified** —
   `connect_test.go` runs the generated grpc-go stub and the Python client's code path against
   the Connect handler unchanged. What differs is not the RPCs but the edges: `h2c` rather than
   grpc-go's HTTP/2, so keepalive and max-message-size knobs are configured elsewhere and behave
   differently under load, which this evaluation has not tested. Any migration should run both
   servers side by side under the conformance suite before the default changes.
2. **Do not build the four planned clients on stdio.** It is the better answer to Problem 2 in
   isolation — ~690 lines against ~100, 2 ms faster to start — but it cannot serve a browser at
   all, it forfeits a shared service and cache between processes, and its costs grow rather than
   shrink if streaming arrives (§8.3).
3. **Attack Problem 2 directly instead.** Most of the 690 lines are not a gRPC tax, they are the
   price of *adopting a service this client did not start*. A client that always spawns a private
   child on an ephemeral port (port 0, port reported on stdout or in a per-child state file) drops
   the ownership records, the start-time authentication, the adoption path and the replacement
   path — the 385-line block plus the 101-line record block — while keeping one transport, remote
   use, `curl`, and a shared service as an opt-in for whoever wants it. This is the follow-up
   worth costing next, and it should be answered before three more clients reimplement adoption.
4. **Keep `internal/frontend/stdiorpc`** as the prototype it is, behind the flag. It cost little, it is
   tested, and it is the right transport for one future case: an editor extension or CLI that
   already spawns a child, as `cmd/sysml-lsp` does.
5. **Conformance across transports.** The suite being built under `conformance/` should take the
   transport as a fixture parameter rather than assuming a channel: one case list run against
   grpc-go, Connect-protobuf, Connect-JSON and stdio, asserting identical results and identical
   status codes. `bench_transports.py` already demonstrates the shape — one `Transport` interface
   with a `call(method, request, response_type)` method and four implementations. The
   JSON-specific edges this evaluation hit are exactly what such a suite must cover: `int64` as a
   string, `oneof` fields that reject being set twice, and error shape. Without that
   parameterization, adopting Connect doubles the untested surface instead of doubling the tested
   one.
